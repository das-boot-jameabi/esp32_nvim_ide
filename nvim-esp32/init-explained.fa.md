# شرح فنی init.lua

این متن بر اساس [فایل فعلی](init.lua) نوشته شده است. فایل از بالا به پایین با Lua اجرا می‌شود و هیچ plugin manager یا افزونهٔ شخص ثالثی بارگذاری نمی‌کند. `vim` رابط Lua داخلی Neovim است.

## ۱. معماری و جریان اطلاعات

```text
init.lua
  ├─ گزینه‌های ویرایشگر و میان‌برها
  ├─ پیکربندی و فعال‌کردن client داخلی LSP
  │     └─ clangd به‌عنوان یک فرایند جداگانه
  │           ├─ متن bufferهای باز از مسیر LSP
  │           ├─ compile_commands.json از روی دیسک
  │           └─ پرس‌وجو از cross-compiler مجاز برای includeها و target
  └─ فرمان‌های Pio در ترمینال داخلی
        └─ PlatformIO → toolchain مخصوص ESP32 / آپلود / سریال
```

Neovim کلاینت LSP است؛ clangd سرور زبان است. ارتباط معمول این دو با پیام‌های JSON-RPC روی stdin/stdout فرایند سرور انجام می‌شود. کلاینت بازشدن و تغییر متن را به سرور اطلاع می‌دهد و درخواست‌هایی مانند completion، definition و rename می‌فرستد؛ سرور پاسخ و diagnostics را برمی‌گرداند.

clangd کد ذخیره‌نشدهٔ buffer باز را از LSP می‌بیند، اما build واقعی PlatformIO فایل‌های روی دیسک را می‌خواند. ذخیرهٔ فایل پیش از build این دو دید را هماهنگ می‌کند.

## ۲. گزینه‌های عمومی ویرایشگر

`vim.g.mapleader = ' '` متغیر سراسری Leader را روی Space می‌گذارد. این خط قبل از تعریف میان‌برها آمده، چون `<leader>` هنگام تعریف mapping با مقدار همان زمان جایگزین می‌شود.

`vim.opt` رابط تنظیم optionهاست:

| گزینه | مقدار | اثر |
|---|---|---|
| `number` | `true` | نمایش شمارهٔ خط فعلی در کنار شماره‌های نسبی |
| `relativenumber` | `true` | نمایش فاصلهٔ خطوط دیگر تا خط فعلی؛ مناسب حرکت‌هایی مثل `5j` |
| `expandtab` | `true` | درج فاصله به‌جای Tab برای تورفتگی |
| `shiftwidth` | `4` | اندازهٔ هر مرحلهٔ تورفتگی |
| `tabstop` | `4` | عرض نمایش کاراکتر Tab موجود در فایل |
| `smartindent` | `true` | تورفتگی خودکار ساده برای ساختارهای شبیه C؛ formatter کامل نیست |
| `ignorecase` | `true` | جست‌وجوی بدون حساسیت به بزرگی حروف |
| `smartcase` | `true` | حساس‌کردن جست‌وجو هنگامی که الگو حرف بزرگ دارد |
| `termguicolors` | `true` | استفاده از رنگ‌های true color در ترمینال سازگار |
| `signcolumn` | `'yes'` | نگه‌داشتن ستون نشانه‌ها برای diagnostics و جلوگیری از جابه‌جایی متن |
| `updatetime` | `250` | زمان برخی رویدادهای idle مانند CursorHold و نوشتن swap؛ سرعت pollingِ LSP یا build را تعیین نمی‌کند |
| `completeopt` | `menu,menuone,noselect` | نمایش منوی تکمیل حتی برای یک نتیجه، بدون انتخاب خودکار اولین مورد |
| `clipboard` | `'unnamedplus'` | استفاده از clipboard سیستم برای عملیات معمول کپی/چسباندن، در صورت وجود provider مناسب |

`tabstop` فایل موجود را بازنویسی نمی‌کند و این گزینه‌ها استاندارد قالب‌بندی کل پروژه را تحمیل نمی‌کنند.

## ۳. پیدا کردن مسیر خانه و clangd

```lua
local home = vim.fn.expand('~'):gsub('\\', '/')
local clangd = vim.fn.exepath('clangd')
if clangd == '' then clangd = 'C:/Program Files/LLVM/bin/clangd.exe' end
```

`vim.fn` امکان فراخوانی توابع داخلی Vimscript از Lua را می‌دهد. `expand('~')` مسیر خانهٔ کاربر را برمی‌گرداند. `gsub` بک‌اسلش‌های ویندوز را به `/` تبدیل می‌کند؛ در رشتهٔ Lua، `'\\'` یک بک‌اسلش واقعی را بیان می‌کند. متغیر `home` فقط نتیجهٔ اول `gsub`، یعنی رشتهٔ تبدیل‌شده، را می‌گیرد.

`exepath` فایل اجرایی را در PATH جست‌وجو می‌کند. اگر پیدا نشود، مسیر رایج نصب LLVM استفاده می‌شود. این fallback وجود فایل را بررسی نمی‌کند؛ اگر مسیر اشتباه باشد، شروع LSP شکست می‌خورد. بنابراین یک clangd در PATH بر نسخهٔ نصب‌شده در Program Files اولویت دارد.

## ۴. ثبت پیکربندی clangd

`vim.lsp.config('clangd', {...})` پیکربندی کلاینتی با نام clangd را ثبت می‌کند. برای این کار به افزونهٔ `nvim-lspconfig` نیاز نیست. ثبت پیکربندی به‌تنهایی سرور را برای هر فایل دلخواه شروع نمی‌کند.

### cmd و گزینه‌های سرور

`cmd` یک لیست است: عضو اول executable و اعضای بعدی آرگومان‌ها هستند. مسیر دارای فاصله مثل `Program Files` یک عضو مستقل است؛ نباید علامت نقل‌قول shell را به داخل خود مسیر اضافه کرد.

| آرگومان | نقش |
|---|---|
| `--background-index` | ساخت index در پس‌زمینه برای نمادها و ارجاع‌های پروژه، با استفاده از اطلاعات compilation database |
| `--clang-tidy` | فعال‌کردن بررسی‌های clang-tidy در چارچوب قابلیت‌ها و تنظیمات clangd؛ جایگزین همهٔ بررسی‌های toolchain نیست |
| `--completion-style=detailed` | درخواست قالب جزئی‌تر آیتم‌های تکمیل |
| `--header-insertion=never` | جلوگیری از افزودن خودکار include توسط تکمیل؛ includeهای موجود را حذف نمی‌کند |
| `--query-driver=...` | تعیین فهرست مجاز درایورهایی که clangd می‌تواند برای کشف مشخصات toolchain اجرا کند |

الگوی فعلی query-driver برابر `~/.platformio/packages/**/bin/*` است. `**` پوشه‌های میانی و `*` نام فایل را پوشش می‌دهد. clangd با این اجازه می‌تواند درایور ذکرشده در فرمان کامپایل را برای یافتن system includeها و اطلاعات target پرس‌وجو کند. این الگو خودش کامپایلر انتخاب نمی‌کند و ابزار دانلود نمی‌کند؛ کامپایلر اصلی از فرمان ثبت‌شده در database می‌آید.

این مجوز در محدودهٔ پوشهٔ پکیج‌های PlatformIO است، ولی همهٔ فایل‌های زیر bin آن‌ها را پوشش می‌دهد. برای محدودکردن بیشتر می‌توان مسیر دقیق cross-compilerهای مورد استفاده را جایگزین کرد. اگر PlatformIO جای دیگری نصب باشد، این الگو نیز باید تغییر کند.

پرس‌وجو از درایور به معنای تبدیل clangd به GCC مخصوص Xtensa نیست. تحلیل همچنان با زیرساخت Clang انجام می‌شود؛ ناسازگاری target یا flags ممکن است باقی بماند.

### filetypes و root_markers

`filetypes = { 'c', 'cpp' }` اتصال خودکار این تنظیم را به bufferهای دارای این filetypeها محدود می‌کند. فایل‌های هدر بسته به تشخیص Neovim ممکن است c یا cpp باشند. پسوند `.ino` مستقیماً در این فهرست نیست؛ در پروژهٔ Arduino با PlatformIO معمولاً از `src/main.cpp` استفاده می‌شود.

`root_markers` نشانه‌های جست‌وجوی ریشهٔ workspace را مشخص می‌کند: `platformio.ini`، `compile_commands.json` و `.git`. Neovim با جست‌وجو در مسیر فایل و والدها، ریشه را طبق قواعد root markers تشخیص می‌دهد. در پروژه‌های PlatformIO، فایل `platformio.ini` مرز مناسب هر پروژه را مشخص می‌کند.

تشخیص ریشهٔ LSP و پیدا کردن compilation database دو کار مرتبط اما جدا هستند. clangd معمولاً database را از مسیر فایل و والدهای آن جست‌وجو می‌کند. وجود marker به‌تنهایی ثابت نمی‌کند database موجود، تازه یا درست است.

## ۵. چرا compile_commands.json مهم است؟

برای تحلیل یک فایل C/C++، دانستن متن کافی نیست. لازم است زبان، استاندارد، defineها، مسیر includeها و فرمان toolchain مشخص باشند. PlatformIO هدف `compiledb` را برای ثبت این اطلاعات دارد.

هر ورودی database معمولاً شامل `directory`، `file` و یکی از `command` یا `arguments` است. clangd این اطلاعات را مبنای تحلیل قرار می‌دهد و آن را برای استفادهٔ داخلی سازگار می‌کند. این فایل محل تعریف library dependency نیست؛ وابستگی‌ها همچنان در تنظیم PlatformIO مدیریت می‌شوند.

برای هدرها ممکن است فرمان مستقلی در database نباشد؛ clangd تنظیم مناسب را از فایل منبع مرتبط استنباط می‌کند. نبودن یا قدیمی‌بودن database می‌تواند باعث missing header، unknown identifier یا انتخاب شاخهٔ اشتباه `#ifdef` شود.

هدف compiledb معمولاً ساخت و لینک کامل firmware یا آپلود انجام نمی‌دهد، اما ممکن است پیش از تولید database وابستگی‌ها و فایل‌های لازم را آماده کند. تغییر environment، framework، کتابخانه یا build flags دلیل تولید دوبارهٔ آن است.

## ۶. تنظیم نمایش diagnostics

`vim.diagnostic.config` نمایش diagnostics را به‌صورت عمومی تنظیم می‌کند:

- `virtual_text`: نمایش متن کوتاه خطا کنار خط.
- `signs`: نشانه در ستون کناری.
- `underline`: خط‌کشیدن زیر محدودهٔ مسئله.
- `severity_sort`: ترتیب‌دهی بر اساس شدت.
- `update_in_insert = false`: به‌روز نکردن نمایش diagnostics هنگام Insert؛ این گزینه ارسال تغییر متن به سرور یا تحلیل در پس‌زمینه را متوقف نمی‌کند.

diagnostic الزاماً خطای build نیست؛ ممکن است هشدار، پیشنهاد یا نتیجهٔ تحلیل clangd باشد. خروجی واقعی GCC و linker در ترمینال PlatformIO مستقل است.

## ۷. رویداد LspAttach و میان‌برهای محلی

autocmd با نام رویداد `LspAttach` پس از اتصال یک LSP به buffer اجرا می‌شود. تابع callback دو دادهٔ اصلی را استفاده می‌کند:

- `event.data.client_id`: شناسهٔ کلاینتی که متصل شده است.
- `event.buf`: شناسهٔ buffer مقصد.

`get_client_by_id` شیء کلاینت را می‌گیرد و `supports_method('textDocument/completion')` بررسی می‌کند که سرور تکمیل کد را پشتیبانی می‌کند. فقط در این صورت تکمیل داخلی با `vim.lsp.completion.enable` فعال می‌شود.

`autotrigger = true` یعنی Neovim می‌تواند با triggerهای تکمیل سرور درخواست خودکار بفرستد؛ این گزینه لزوماً بعد از هر حرف منو باز نمی‌کند. `Ctrl+Space` مستقیماً `vim.lsp.completion.get` را برای درخواست دستی صدا می‌زند.

تابع محلی `map` از `vim.keymap.set` برای حالت Normal و با گزینهٔ `buffer = event.buf` استفاده می‌کند. در نتیجه کلیدهای LSP فقط برای buffer متصل تعریف می‌شوند:

| نگاشت | تابع | درخواست یا عمل |
|---|---|---|
| `gd` | `vim.lsp.buf.definition` | درخواست محل تعریف |
| `gr` | `vim.lsp.buf.references` | درخواست محل‌های ارجاع |
| `K` | `vim.lsp.buf.hover` | اطلاعات نماد |
| `<leader>rn` | `vim.lsp.buf.rename` | درخواست rename و اعمال ویرایش‌های workspace |
| `<leader>ca` | `vim.lsp.buf.code_action` | درخواست اقدام‌های اصلاحی |
| `<leader>e` | `vim.diagnostic.open_float` | نمایش محلی diagnostics ثبت‌شده |
| `<leader>q` | `vim.diagnostic.setqflist` | انتقال diagnostics به quickfix |

دو عمل آخر برای نمایش داده‌های موجود در Neovim هستند؛ الزاماً درخواست تازه‌ای به سرور نمی‌فرستند. rename می‌تواند چند فایل را تغییر دهد؛ تغییرات را پیش از build مرور و ذخیره کن.

این autocmd فیلتر نام کلاینت ندارد؛ اگر بعداً LSP دیگری اضافه شود، روی اتصال آن هم اجرا می‌شود. همچنین augroup با `clear = true` ندارد، بنابراین sourceکردن چندبارهٔ فایل، callbackهای تکراری ثبت می‌کند. راه فعلیِ مطمئن برای اعمال تغییر، راه‌اندازی دوبارهٔ Neovim است.

پس از ثبت callback، `vim.lsp.enable('clangd')` فعال‌سازی خودکار تنظیم را درخواست می‌کند. ترتیب مهم است: callback پیش از اتصال سرور آماده است.

## ۸. نگاشت‌های عمومی

`<leader>w` فرمان `write` را اجرا می‌کند و فقط buffer فعلی را ذخیره می‌کند. `<leader>f` فرمان `Explore` از مرورگر داخلی netrw را اجرا می‌کند؛ این یک fuzzy finder نیست.

نگاشت حالت `t` برای `<Esc><Esc>`، توالی `<C-\><C-n>` را می‌فرستد. این توالی از Terminal-mode به Terminal-Normal-mode می‌رود؛ فرایند ترمینال همچنان فعال می‌ماند. دو Esc پشت سر هم با رعایت timeout نگاشت دریافت می‌شوند.

`<cmd>...<CR>` قالب اجرای فرمان در mapping است و `<CR>` نقش Enter را دارد. mappingهای Lua تابع را به‌عنوان callback نگه می‌دارند؛ تابع هنگام فشردن کلید اجرا می‌شود، نه هنگام خواندن init.lua.

## ۹. تابع platformio(args)، مرحله‌به‌مرحله

### پیدا کردن ریشه

```lua
local root = vim.fs.root(0, { 'platformio.ini' })
  or vim.fs.root(vim.fn.getcwd(), { 'platformio.ini' })
```

`0` به buffer فعلی اشاره می‌کند. ابتدا از مسیر فایل فعلی به‌سمت والدها برای `platformio.ini` جست‌وجو می‌شود. اگر نتیجه nil باشد، به‌کمک عملگر کوتاه‌مدار `or` از پوشهٔ جاری جست‌وجو می‌شود. این جست‌وجو از هر نقطه به داخل همهٔ زیرپوشه‌ها نمی‌رود؛ بنابراین بازکردن Neovim در پوشهٔ بالاترِ چند پروژه، بدون بازکردن فایل پروژه، ممکن است ریشه‌ای پیدا نکند.

نبودن root با `vim.notify` در سطح ERROR گزارش می‌شود و `return` اجرای تابع را متوقف می‌کند.

### پیدا کردن executable

ابتدا `exepath('pio')` از PATH استفاده می‌کند. اگر نتیجه خالی باشد، مسیر ویندوزی `home .. '/.platformio/penv/Scripts/pio.exe'` ساخته می‌شود. عملگر `..` اتصال رشته‌ها در Lua است.

`vim.fn.executable(pio) ~= 1` یعنی executable معتبر پیدا نشده؛ در این حالت تابع پیام می‌دهد و برمی‌گردد. این fallback برای نصب فعلی ویندوز نوشته شده و برای Linux یا محل نصب متفاوت باید تغییر کند.

### ذخیره و ساخت پنجره

`vim.cmd('wall')` فرمان Ex برابر `:wall` را اجرا می‌کند: نوشتن همهٔ bufferهای تغییرکردهٔ قابل‌نوشتن. خطای نوشتن در این کد با `pcall` گرفته نمی‌شود؛ پس قبل از ساخت پنجره و job اجرا را متوقف می‌کند.

`botright 14new` یک پنجرهٔ افقی تازه در پایین باز می‌کند و ارتفاع اولیهٔ ۱۴ خط را درخواست می‌دهد. Neovim با توجه به فضای موجود ممکن است اندازه را تطبیق دهد.

### اجرای فرایند

```lua
vim.fn.jobstart(vim.list_extend({ pio }, args), {
  term = true,
  cwd = root,
})
```

`vim.list_extend` آرگومان‌ها را به لیست تازهٔ `{ pio }` اضافه می‌کند. برای build نتیجه چیزی شبیه `{ '.../pio.exe', 'run' }` است. اجرای لیست آرگومان از چسباندن رشته و عبور از shell اجتناب می‌کند؛ مسیرهای دارای فاصله مستقل باقی می‌مانند.

`jobstart` فرایند را به‌صورت asynchronous اجرا می‌کند؛ رابط Neovim منتظر اتمام build مسدود نمی‌شود. `term = true` خروجی و ورودی را به buffer ترمینال فعلی وصل می‌کند. `cwd = root` پوشهٔ کاری فرایند فرزند را تنظیم می‌کند، بدون اینکه الزاماً پوشهٔ جاری خود Neovim تغییر کند.

`startinsert` ورودی ترمینال را فعال می‌کند تا کلیدها به برنامه فرستاده شوند. این خط منتظر پایان فرایند نمی‌ماند.

کد شناسهٔ job، exit callback و تبدیل خطاها به quickfix را نگه نمی‌دارد؛ موفقیت یا شکست را باید از خروجی ترمینال خواند. اجرای چندباره پنجره و job تازه می‌سازد و قفل سطح ویرایشگر برای جلوگیری از اجرای موازی ندارد.

## ۱۰. فرمان‌های سفارشی و نگاشت آن‌ها

`nvim_create_user_command` فرمان Ex می‌سازد. callback هر فرمان، تابع مشترک را با لیست آرگومان مناسب فراخوانی می‌کند:

| فرمان Neovim | مقدار args | اثر |
|---|---|---|
| `PioBuild` | `{ 'run' }` | ساخت با محیط‌های پیش‌فرض PlatformIO |
| `PioUpload` | `{ 'run', '-t', 'upload' }` | ساخت در صورت نیاز و آپلود |
| `PioMonitor` | `{ 'device', 'monitor' }` | اجرای مانیتور سریال |
| `PioCompdb` | `{ 'run', '-t', 'compiledb' }` | تولید compilation database |

جدول گزینهٔ خالی `{}` یعنی آرگومان کاربری تعریف نشده است؛ مثلاً `:PioBuild -e test` پشتیبانی نمی‌شود. انتخاب environment و پورت از تنظیم PlatformIO یا فرمان مستقیم انجام می‌شود. نام محیط به پروژه تعلق دارد و در این فایل تنظیم ثابت نشده است.

سه mapping آخر، فرمان‌های Build، Upload و Monitor را به Leader متصل می‌کنند. Compdb فقط فرمان دارد. mappingها در حالت Normal هستند؛ هنگام تمرکز روی ترمینال ابتدا باید از حالت ورودی ترمینال خارج شوی.

## ۱۱. مرز مسئولیت‌ها و محدودیت‌های فعلی

- Neovim و clangd مسئول تجربهٔ ویرایش و تحلیل‌اند؛ cross-compiler PlatformIO خروجی firmware را تولید می‌کند.
- تنظیم هیچ toolchain، کتابخانه یا LSP server را دانلود نمی‌کند.
- ساخت database و آغاز LSP مستقل‌اند؛ اتصال سالم سرور، درستی database را ثابت نمی‌کند.
- جزئیات برد، framework، baud rate، build flags و کتابخانه‌ها در `platformio.ini` هستند.
- خطاهای linker، ظرفیت flash، partition و خطاهای زمان اجرا ممکن است فقط هنگام build یا روی برد دیده شوند.
- قابلیت debug سخت‌افزاری، DAP، OpenOCD/GDB، format-on-save، fuzzy finder و مدیریت snippet در این فایل پیاده نشده است.
- کد برای reload تکراری بدون ایجاد autocmd اضافی طراحی نشده و مدیریت چرخهٔ jobها حداقلی است.

این محدودیت‌ها کمک می‌کنند هنگام عیب‌یابی مشخص شود مسئله به نمایش ویرایشگر، تحلیل زبان، تنظیم پروژه، کامپایل یا ارتباط با سخت‌افزار تعلق دارد.
